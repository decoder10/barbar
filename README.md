# Barbar Cafe · Art Gallery

Самостоятельное приложение на **React + TypeScript + Node.js** для меню, закупок, рецептов, продаж и отчётов. Портфолио — другой проект; файлы Barbar находятся только в этом репозитории.

## Локальный запуск и MongoDB

Требуются Node.js **22.12+** (или Node.js 24) и Docker Desktop. Рабочие данные хранятся в **MongoDB**, а JSON используется для первоначального переноса и экспорта резервных копий.

```sh
npm ci
# Перед первым запуском: скопировать .env.example в .env и задать два разных пароля.
npm run db:start
npm run dev
```

Открыть **http://localhost:4001**. React и Node API запускаются одной командой. Порт фиксирован. `npm run db:start` запускает MongoDB 8.0 с replica set, необходимым для транзакций; доступ открыт только на `127.0.0.1:27017`. Данные сохраняются в постоянном Docker-томе `barbar_barbar-mongodb`. `npm run db:stop` останавливает базу, сохраняя данные. Не удаляйте Docker-том для очистки истории.

В `.env`:

- `BARBAR_USERNAME=barbar`, `BARBAR_PASSWORD` — учётная запись сотрудника;
- `BARBAR_ADMIN_USERNAME=admin`, `BARBAR_ADMIN_PASSWORD` — отдельная учётная запись владельца;
- оба пароля от 12 символов; пароль с `#` в `.env` нужно заключать в кавычки;
- `BARBAR_MONGODB_URI` — подключение к MongoDB; локально по умолчанию `mongodb://127.0.0.1:27017/?replicaSet=rs0&directConnection=true`;
- `BARBAR_MONGODB_DATABASE=barbar` — имя базы.

Пароли и URI не добавляются в Git и не используют префикс `VITE_`. На компьютере владельца `.env` уже настроен. При первом запуске эти переменные создают в MongoDB начальные аккаунты: `admin` — Грач (владелец), `barbar` — Ника (работник). Дальше пользователи и роли читаются из БД; изменение переменных не перезаписывает существующие пароли. Пароли хранятся как salted scrypt-хеши. Случайный токен находится в HttpOnly-cookie, его SHA-256 — в коллекции `sessions`; срок сессии 12 часов. Старые сессии после обновления требуют повторного входа.

## Права доступа

**`barbar`** видит только продажи: каталог без цен, форму записи количества, количество по каждой позиции и записи за выбранный день. Отменённые продажи помечены и исключены из итогов. Разрешены запись новых продаж и создание коктейлей: название, категория, изображение и рецепт в мл/г. В форме создания нет денежных полей. Новая позиция сохраняется без заданной продажной цены; администратор задаёт её перед первой продажей. Сотрудник может создавать коктейли и редактировать состав существующих рецептов без денежных полей. Склад доступен только для просмотра, включая отсутствующие позиции; закупки, изменение склада, цены и отмены продаж запрещены.

**`admin` / владелец** создаёт аккаунты через «Пользователи», задаёт имя, логин, пароль, роль (владелец/работник), email и телефон. Имеет полный доступ: склад, закупки, меню и рецепты, цены, продажи и отмены, денежные отчёты, экспорт, восстановление и очистка истории.

Ограничения проверяются на сервере. Ответы API для `barbar`, включая ответ на новую продажу и повтор запроса, не содержат закупок, закупочных цен, себестоимости, выручки, состава с расходами или полных резервных копий. Прямой переход на административный адрес возвращает сотрудника в продажи, а запрещённые API-команды получают `403`.

## Netlify и MongoDB Atlas

1. Создать MongoDB Atlas cluster (подойдёт Free), пользователя базы и настроить Network Access для среды Functions. Использовать отдельного пользователя приложения с доступом `readWrite` к его базе.
2. В Netlify подключить репозиторий. `netlify.toml` содержит build `npm run build`, publish `dist`, functions `netlify/functions`, Node.js 22.
3. В серверных Environment variables установить `BARBAR_PASSWORD`, отдельный `BARBAR_ADMIN_PASSWORD`, `BARBAR_MONGODB_URI` из Atlas (формат `mongodb+srv://...`) и `BARBAR_MONGODB_DATABASE=barbar`. По желанию задать логины. В интерфейсе Netlify вводить пароль без обрамляющих кавычек.
4. Выполнить deploy. Без MongoDB URI сервер не переключается обратно на файлы и не подтверждает сохранение данных.
5. Проверить входы `admin` и `barbar`. Настроить домен. Прямые переходы `/inventory`, `/cocktails`, `/reports`, `/files` поддерживаются для администратора.

Предпросмотры используют отдельную базу `<имя>_preview_<deploy-id>`, чтобы не менять рабочую. Пользователь MongoDB для preview должен иметь права на соответствующую отдельную базу; новый preview deploy начинает с отдельного пустого учёта; можно задать отдельные credentials в preview context. Локальная БД не загружается в Atlas автоматически: скачайте полную резервную копию локально и восстановите её на сайте под `admin`.

Просто загрузить `dist` недостаточно: нужны Node Functions и доступ к MongoDB. На момент изменения проекта Atlas и удалённый deploy автоматически не создаются — требуется аккаунт владельца и строка подключения.

Документация: [создание Atlas cluster](https://www.mongodb.com/docs/atlas/tutorial/deploy-free-tier-cluster/), [подключение приложения](https://www.mongodb.com/docs/atlas/connect-to-database-deployment/), [транзакции драйвера](https://www.mongodb.com/docs/drivers/node/v6.x/crud/transactions/).

## Рабочий порядок

1. **Склад:** при необходимости создать ингредиент. Для алкоголя/жидкостей — миллилитры и цены за 1 000 мл. Для фруктов, сахара и специй — граммы и цены за 1 000 г. Затем добавить закупку с количеством, датой и фактической ценой. 1 000 + 1 000 = 2 000 единиц на складе.
2. **Меню и рецепты:** выбрать позицию, нажать карточку, добавить состав на одну продаваемую порцию. Для настойки указывается расход алкоголя, ягод, сахара и других ингредиентов на порцию; для сета — на полный сет. Это расчёт расхода на продажу, без отдельного производственного учёта партий настоек.
3. **Себестоимость** вычисляется из состава по средней стоимости оставшегося запаса. **Цена продажи** — отдельное редактируемое поле. Кнопка расчёта с наценкой лишь предлагает цену; её нужно применить явно. Изменение закупочных цен само по себе продажную цену не меняет.
4. **Продажи:** выбрать дату, нажать карточку, ввести число порций либо миллилитры алкоголя в розлив. Сервер проверит остатки и запишет продажу вместе со списаниями. Пустой состав блокирует продажу позиции меню. Недостаток ингредиентов и продажи до закупки запрещены.
5. **Отчёты:** день или месяц, выручка, стоимость проданных ингредиентов, валовая прибыль, закупки, продажи по позициям и расход ингредиентов. Часовой пояс — Ереван, валюта — AMD ֏. CSV содержит строки продаж, включая отметки об отменах; отмены исключены из итогов.

Историческая продажа хранит название, категорию, состав, сумму выручки и стоимость каждого списания. Редактирование рецепта или прайс-листа не меняет прошлые отчёты. Отмена продажи возвращает ингредиенты и их стоимость на склад.

Валовая прибыль = выручка − ингредиенты. Аренда, зарплаты, налоги и другие расходы не включены.

## Меню и изображения

В `src/barbar/data/cocktails.json` внесены **167 позиций и вариантов** из предоставленного меню: коктейли, настойки, шоты, сеты, пиво, закуски, горячие и безалкогольные напитки, вина. Название файла сохранено для совместимости с исходной моделью, в интерфейсе это «Меню и рецепты».

Продажные цены внесены с фотографий. Составы не выдуманы и по умолчанию пусты: заполните их через редактор. Цены напитков из раздела **50 ML** пересчитаны в прайс за 1 000 мл умножением на 20. Парные цены вин разнесены на «бокал» и «бутылка»; фактические объёмы нужно указать в рецепте. `Your cocktail` имеет нулевую цену, которую надо задать вручную. У `Sujuck` на фото есть рукописная правка: внесено 1 500 ֏, эту строку следует сверить.

Фотографии карточек иллюстративные, выбираются в редакторе из 64 вариантов с названиями и группами. Для существующего меню изображение подбирается по названию и категории автоматически; ручной выбор сохраняется. Логотип восстановлен по предоставленной вывеске. Исходная фотография стены/вывески не используется на сайте и не включена в репозиторий.

## Хранение, перенос и резервные копии

MongoDB содержит коллекции `alcohol`, `cocktails`, `purchases`, `sales`, `stockResets` и служебную `state`, а также отдельные `users` и `sessions`. Каждая продажа — отдельный документ, история индексируется по дате. Сохранение использует транзакцию и проверку версии: каталог, закупки, продажи и списания изменяются согласованно. Две кассы не могут списать один остаток дважды; повтор одной операции не создаёт вторую продажу.

При первом обращении к пустой базе сервер загружает прежнее хранилище:

- локально — `.barbar-data/data.json` и связанные файлы `.barbar-data/sales/`;
- на Netlify — прежний store Netlify Blobs `barbar-cafe-v1`; при его отсутствии проверяется `barbar-cafe-preview-local`, который использовала старая версия без runtime-переменной `CONTEXT`. Предпросмотры не импортируют рабочую историю.

Перенос проверяет формат и остатки, затем импортирует все данные одной транзакцией. Ошибка чтения или проверки прерывает перенос, не подменяя историю пустыми данными. После успешного импорта MongoDB становится единственным рабочим хранилищем. Исходные JSON/Blobs остаются нетронутыми как копия до переноса; новые операции в них не записываются. Для переноса остановите старую версию приложения на время переключения: записи старого сервера после импорта не синхронизируются с MongoDB.

В **«Данные и копии»** администратор может скачать полную JSON-копию, экспортировать отдельный день и удалить продажи **строго раньше выбранной даты**. Удаление выполняется в транзакции: подробные документы удаляются, суммарный расход и его стоимость сохраняются, количество и стоимость запасов не меняются. Операции в очищенном периоде закрыты; отчёты за него недоступны. Восстановление — из полной копии.

JSON-формат резервных копий совместим с предыдущей версией. Ограничение рабочего снимка **3 МБ** пока сохранено для ответов Netlify Functions и импорта; это ограничение текущего API, а не MongoDB. Пагинация большой многолетней истории требует отдельной доработки.

```text
  services/                     # HTTP-клиент
  ui/                           # общие элементы интерфейса
  pages/                        # продажи, склад, меню, отчёты, файлы
  styles/                       # SCSS, токены, темы и миксины
  **/__tests__/                 # модульные тесты рядом со своей областью

```

### Сброс отдельного остатка

В строке напитка на странице «Склад» нажмите «Сброс». Окно покажет название, списываемое количество, нулевой новый остаток и стоимость списания. Для подтверждения введите «СБРОС». При нулевом остатке кнопка недоступна. Если другой сотрудник изменил остаток или его стоимость, нужно обновить склад и подтвердить заново.

Сброс сохраняется в истории списаний и полной резервной копии; закупки, рецепты и продажи остаются. Это не продажа и не выручка. Стоимость списания показана отдельно на складе, отчёт о валовой прибыли по продажам её не вычитает. Новая закупка снова пополняет остаток. Отмена прошлой продажи, как обычно, возвращает её ингредиенты на склад.

### Ошибки в закупке и продукты в рецептах

В истории закупок нажмите «Исправить / удалить» и укажите фактически купленное количество. Разница изменит склад и сумму закупки. Полное удаление требует ввода «УДАЛИТЬ». Исправление блокируется, если нарушает историю продаж/списаний или относится к очищенному периоду.

На складе есть отдельный фильтр «Продукты и миксеры»: фрукты, ягоды, соки, молоко, сливки, сахар, лёд, специи. Можно добавлять собственные продукты. Рецепт поддерживает точное количество в мл/г и раздел «Продукты: стоимость на порцию». Например, лимон 50 ֏ плюс лёд 20 ֏ добавят 70 ֏ к себестоимости каждой порции, без списания количества. Такой расход фиксируется в продаже и сохраняет старую сумму после редактирования рецепта. Не добавляйте один продукт одновременно обоими способами; редактор и сервер исключают двойной учёт. Фактические закупочные расходы и примерная себестоимость порций остаются разными показателями.

64 новых иллюстрации находятся в public/barbar/menu-*-v2.jpg. Использован встроенный image_gen; полные запросы — в docs/menu-images.md.

### Пиво, вино и коньяк по бутылкам

В «Складе» есть кнопки «Новое пиво», «Новое вино», «Новый коньяк». Каждая марка и фасовка — отдельная позиция с собственными закупочной и продажной ценами за бутылку. Объём выбирается из 300, 330, 500, 700, 750, 1 000 мл или задаётся вручную. Закупки вводятся целыми бутылками.

Для вина и коньяка можно указать объём бокала/порции в мл и отдельную цену порции. Бутылка и порция автоматически связываются с одним складским остатком. Например, шесть бокалов по 125 мл списывают бутылку 750 мл. Объём уже закупленной бутылки менять нельзя: для другой фасовки создайте новую позицию. Менять цену и объём будущей порции можно; сохранённые продажи не пересчитываются.

После обновления MongoDB автоматически добавляет складские марки из ещё не настроенных и не проданных позиций пива и винных бутылок в меню. Цены меню сохраняются, закупки не создаются. Ранее использовавшиеся позиции в мл и их история не переводятся в бутылки без данных о фасовке. Добавляются отдельные Bacardi белый/тёмный и бутылочные варианты Ararat; их закупочные цены и неизвестные цены за бутылку задаёт администратор.

В JSON сохранены совместимые имена `ml`, `costPerLiter`, `pricePerLiter`: для ингредиента с `unit: "bottle"` количество означает бутылки, а цены — стоимость одной бутылки. Для `ml`/`g` цены по-прежнему за 1 000 единиц. Сотруднику выдаются только название, доступность и количество, без цен и финансовых отчётов. Новые переменные окружения Netlify не нужны; достаточно публикации обновлённого коммита.

### Склад сотрудника

Учётная запись `barbar` видит «Склад → Наличие и остатки»: марки, единицы, остатки, категории и фильтр «Нет в наличии». Интерфейс только для просмотра, без цен, закупок, редактирования, сброса и выгрузки данных. Сервер передаёт отдельный список разрешённых полей и отклоняет команды изменения склада с HTTP 403 до чтения базы. Сотрудник по-прежнему может записывать продажи и добавлять рецепты.

### Меню и рецепты сотрудника

В `barbar` доступен раздел «Меню и рецепты» с изображениями, поиском и категориями. Сотрудник добавляет новые коктейли, меняет ингредиенты/количества и инструкции существующих рецептов. Цены, себестоимость и суммы дополнительных расходов отсутствуют в интерфейсе и серверном ответе. Сервер принимает отдельную команду `updateRecipe`, сохраняющую цены, административные расходы и прошлые продажи; устаревшая версия рецепта не перезаписывается. Бутылки и порции, связанные со складом, доступны только для просмотра.

Склад сотрудника показывает изображения напитков. Позиции с нулевым остатком выделены красным и идут первыми; фильтр «Нет в наличии» сохраняется. В карточке рецепта и редакторе показано, каких ингредиентов не хватает на порцию. Закупки, редактирование склада и его сброс сотруднику недоступны.

## Барный день

Новый день начинается в 06:00 по `Asia/Yerevan`. Продажи до 05:59 включительно относятся к предыдущей дате. Текущая смена определяется сервером при записи продажи; интерфейс переключается автоматически. Исторические записи сохраняют свою дату. В отчётах, экспорте и итогах используется дата смены; `createdAt` хранит фактическое время операции.

Коллекции пользователей и сессий не входят в JSON-экспорт учёта и не заменяются при восстановлении продаж. Для полной резервной копии аккаунтов нужен backup MongoDB. Новые переменные Netlify не требуются: используются уже настроенные MongoDB URI и начальные аккаунты. После обновления нужно войти заново.
