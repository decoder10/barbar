# Резервные копии на компьютере

Выбран пользователем бесплатный MongoDB Atlas. На проверенном кластере нет встроенных резервных копий. Поэтому копии создаются отдельным локальным инструментом, без отправки пользователей и паролей через браузерный API.

## Настройка

1. Скопировать `.env.backup.example` в `.env.backup`, выполнить `chmod 600 .env.backup`.
2. Внести строку Atlas в `BARBAR_BACKUP_MONGODB_URI` **только в этот локальный файл**, не в чат. Для регулярного резервирования рекомендуется отдельный пользователь Atlas с ролью `read` только для БД `barbar`.
3. Указать абсолютный приватный путь к ключу в `BARBAR_BACKUP_KEY_FILE`. При первой копии инструмент создаст случайный ключ AES-256, файл с правами 0600. Сохранить дополнительную копию ключа отдельно от зашифрованных архивов, например в менеджере паролей. Потерянный ключ восстановить нельзя.
4. В `BARBAR_RESTORE_MONGODB_URI` оставить отдельную локальную MongoDB из примера. Это независимый адрес назначения для проверки восстановления, а не рабочий Atlas.

`.env.backup`, файлы `*.backup-key`, `*.barbar-backup` и `.barbar-backups/` исключены из Git. Сам ключ не нужно хранить в общей папке с архивами.

## Запуск

Из каталога проекта:

```sh
npm run db:backup
```

Создаст `.barbar-backups/barbar-ДАТА-ВРЕМЯ.barbar-backup`. В отчёте выводятся только число документов, коллекций и размер. Пароли и документы не выводятся. Архив включает каталог, журнал, пользователей и хеши паролей, аудит, метаданные и индексы; активные сеансы исключены.

После закрытия бара запускать вручную; компьютер должен быть включён и иметь доступ к Atlas. Автоматическое расписание не настроено. Рекомендуемый порядок хранения: семь ежедневных копий и четыре еженедельных. Старые файлы инструмент автоматически не удаляет. Периодически копировать зашифрованные архивы на отдельный носитель: одна копия на том же компьютере не защищает от его потери.

Проверить выбранный архив:

```sh
npm run db:verify -- .barbar-backups/ИМЯ-ФАЙЛА.barbar-backup
```

## Проверка восстановления

Запустить локальную MongoDB `npm run db:start`. Восстанавливать только в **новую** базу с префиксом `barbar_restore_`:

```sh
npm run db:restore -- .barbar-backups/ИМЯ-ФАЙЛА.barbar-backup barbar_restore_check_20260914
```

Сначала проверяются шифрование и контрольная сумма, затем создаются документы и индексы. Существующую базу скрипт не перезаписывает. При ошибке восстановления новая база остаётся с `_restore_in_progress` для диагностики; её нельзя подключать к приложению. Инструмент не переключает рабочий сайт на восстановленную БД.

Для аварийного восстановления рабочего сайта: проверить отдельную восстановленную БД, сверить количества записей, остатки и пользователей, затем осознанно переключить серверное подключение в Netlify и выполнить deploy. Не импортировать поверх живой базы и не запускать `initialData` для восстановления.

## Проверено

`npm run test:backup`: 502 документа в отдельной локальной БД, точное сохранение Date/Decimal128/Long, уникальный индекс пользователей, пустая коллекция, исключение sessions. Неверный ключ, повреждённый архив и попытка записи поверх существующей БД отклонены. Это тест восстановления на синтетических данных; проверка рабочей копии отмечается отдельно в `cloud-security.md`.

Для очень большой БД длительный snapshot может превысить лимит транзакции Atlas. Ошибочная копия удаляется, успешная не объявляется. При таком росте нужны нативные snapshots платного Atlas или процедура `mongodump` с согласованной остановкой записей. Большие копии не следует создавать через Netlify Function.
