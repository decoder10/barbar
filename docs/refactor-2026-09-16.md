# Рефакторинг и ускорение — 16 сентября 2026

Изменения сделаны в рабочей копии и проверены локально. **В Production не опубликованы** — публикация только по отдельному слову владельца.

## Что изменено и почему

### Бэкенд

- **Один запрос карточек вместо двух.** `GET /api/barbar/catalog/cards` принимает `resources=cocktails,alcohol` (не более двух, без повторов; разбор — `parseCardQueries` в `domain/catalog/cards.ts`). Раньше страница «Продажи» при категории «Всё» делала два запроса, и сервер дважды читал остатки и окно популярности. Одиночный запрос сохраняет прежнюю форму ответа.
- **Глубокие страницы истории без пересчёта итогов.** `total` и сводка `groups` за период приходят только с первой страницей; страница по курсору — один индексированный `find`. Клиент (`use-history.ts`) сохраняет загруженные итоги. Раньше каждая страница делала `countDocuments` и агрегацию всего периода.
- **Лента уведомлений** `GET /api/barbar/notifications` (`netlify/lib/notifications/feed.ts`, функция `barbar-notifications.ts`, локальный сервер): что реально было поставлено в очередь push, новые сверху. Владелец видит закупки и остатки, сотрудник — только остатки (то же правило, что при доставке). Коллекции ограничены TTL (сутки/неделя), это лента, не история.
- **Транспорт без дублирования проверок.** Разбор параметров карточек живёт в домене и используется обработчиком и e2e-моком одинаково.

### Фронтенд

- **Утилиты вынесены в свои модули**, страницы их только компонуют: `domain/sales/day-totals.ts` (дневные итоги обеих ролей), `domain/sales/popularity.ts` (окно популярности), `presentation/format-date.ts` (подписи дня и времени), `domain/lookup.ts` (`byId`), `domain/reports/csv.ts` (одно правило CSV), `domain/catalog/recipe-status.ts` (один предикат «рецепт не заполнен» для владельца, сотрудника и сервера).
- **Уведомления разделены по ответственности:** колокольчик в шапке без подписи (`NotificationsButton.tsx`, бейдж — число позиций в дефиците), панель (`NotificationsPanel.tsx` в `ui/drawer.tsx`: тумблер push + лента, строка открывает полный текст), плавающие живые предупреждения (`StockAlerts.tsx`), хуки `use-stock-alerts.ts` и `use-notifications-feed.ts`. Старый `StockNotifications.tsx` удалён.
- **Исправления поведения:** отчёт больше не мутирует кешированный ответ сервера во время рендера (`Reports.tsx`, `consumed`); поиск владельца обрезает пробелы так же, как у сотрудника; сортировка «сначала без рецепта» одинакова у обеих ролей (учитывает управляемые расходы); экспорт сводки больше не удаляет первый символ значений, начинающихся с `= + @ -` — экранирование единое и без потери данных.
- **Найдено по пути:** `clearSessionFilters()` удаляла ключи, перебирая `sessionStorage.key(i)` во время удаления; Chromium меняет порядок ключей после `removeItem`, и один ключ пропускался (проявилось, когда ключей стало 12). Теперь ключи собираются заранее. Регистрация push-подписки (`usePushDevice`) живёт в кнопке уведомлений на всё время работы, а не в панели — иначе каждое открытие панели делало `POST /api/barbar/push`; публичный ключ сервера запрашивается один раз за сессию.
- **Лишние вычисления:** склад не считает остатки второй раз (`inventory.quantities`), оценка запаса без поиска по каталогу на каждый шаг (`unitBasis(a.unit)`), индексы `byId` вместо `.find()` в циклах строк (склад, рецепты, операции); популярность считается только при построении страницы карточек, а не на каждый рендер; значения контекстов `BarProvider`/`SettingsProvider` и их действия мемоизированы — раньше каждый опрос раз в минуту перерисовывал все экраны.
- **Шрифты:** одно семейство Manrope 400–700 (токен `--display`); Playfair Display убран — он весил больше пофайлово и использовался только в заголовках.
- **Чанки:** `react` и `photo-manifest` выделены в отдельные общие чанки (`vite.config.ts`). Самый тяжёлый чанк раньше назывался `photo-catalog`, но состоял в основном из React, а не манифеста.

### Безопасность

- `Strict-Transport-Security` в `netlify.toml`.
- Лимиты запросов на публичных функциях, где их не было: `/api/menu`, `/api/barbar/push`.
- Единое экранирование CSV от формул без потери данных.
- Лента уведомлений отдаёт сотруднику только остатки; суммы закупок не покидают сервер.
- Проверено и оставлено как есть: серверная сборка полей продажи/рецепта (mass assignment закрыт), `SameSite=Strict` + проверка `Origin` на записи, scrypt с KDF для неизвестных логинов, лимит входа 20/мин на IP, отзыв сессий по `authVersion`, allowlist полей сотрудника, кеш отчётов с ролью в ключе.

## Замеры (один компьютер, одинаковые условия)

| Показатель | До | После |
| --- | --- | --- |
| Запросов карточек на `/` при «Всё» | 2 | 1 |
| Запросов БД на страницу истории по курсору | 3 (`find` + `countDocuments` + агрегация периода) | 1 (`find`) |
| История, 50 000 продаж: страница по курсору, холодная | как первая: p95 131,23 мс | p95 2,77 мс, p50 1,16 мс; прочитано 51 документ / 51 ключ |
| Шрифты в сборке | 64 файла, 732 КБ (woff+woff2); Playfair 8 woff2 / 102,7 КБ | 24 woff2, 220 КБ |
| Общий чанк | `photo-catalog` 343,1 КБ / 99,7 КБ gzip (React + манифест вместе) | `react` 216,5 / 67,3; `photo-manifest` 98,5 / 21,7; `photo-catalog` 27,9 / 10,2 |
| `main` | 138,3 / 38,3 КБ gzip | 142,0 / 39,2 (панель уведомлений) |
| Синтетический расчёт остатков (`benchmark.mjs`) | 30,48 → 0,89 мс | без изменений (путь уже индексный) |

Суммарный объём общих чанков не уменьшился (React нужен обеим страницам); изменилась гранулярность кеша: правка фотографий больше не сбрасывает кеш фреймворка. Отчёт «холодный» 359 мс / из кеша 5,6 мс в этом прогоне — прежний документ давал 259 / 0,9 мс; разброс объясняется загрузкой машины, улучшения здесь не заявляется. Последовательные агрегации отчёта внутри одной сессии оставлены сознательно: сессия драйвера MongoDB не допускает параллельных операций.

## Проверки

- `npm run check`: ESLint, TypeScript, 164 модульных теста (добавлены: окно дат, порядок меню при равной популярности, предикат рецепта, разбор `resources`).
- `npm run test:db` в отдельной локальной MongoDB: 36 проверок (добавлены: глубокая страница без итогов, лента уведомлений по ролям).
- `npm run test:load`: 50 000 продаж, целостность остатков и аудита подтверждена.
- `npm run build`: успешно; таблица чанков выше.
- Playwright: 56 сценариев, включая панель уведомлений (список → полный текст, у сотрудника без сумм), объединённый запрос карточек, сортировку по умолчанию, историю с итогами только на первой странице.

## Не проверено или требует отдельного решения

- Production: задержки, холодные старты, доставка push на реальные устройства, планы запросов на Atlas — только после публикации.
- Сжатие манифеста фотографий (98,5 КБ / 21,7 КБ gzip): возможен выигрыш ~2× на gzip, но это отдельная работа с генератором.
- Осталось из аудита фронтенда: общий хук `useUsers` для «Пользователи» и «Журнал», `Backups.tsx` на `snapshotRead`, вынос итогов отчёта из `Reports.tsx` в домен, единая обработка ошибок/загрузки в четырёх страницах с прямым `api()`.
- Настройки облака из `cloud-security.md` (смена пароля Atlas, копии рабочей БД) — решения владельца.
