# Каталог и остатки: протокол 2

Новый клиент посылает `X-Barbar-Protocol: 2`. Старые открытые вкладки без этого заголовка продолжают получать совместимый рабочий снимок; служебные ID операций в нём заменены пустым массивом. Полный экспорт остаётся отдельным запросом владельца `?view=full`.

## Чтение

- `/api/barbar/auth` — сеанс, роль и профиль.
- `GET /api/barbar` с протоколом 2 — `revision`, `catalogRevision` и текущие остатки. Журнала, каталога и ID команд в ответе нет. Запрос читает только метаданные и `stockBalances` в согласованной транзакции; проекция метаданных не читает список служебных ID.
- `GET /api/barbar/catalog` — каталог/рецепты с собственной версией. Проверка прав та же, что у основного API. Для рабочего сервер формирует отдельный allowlist без финансов. Условный запрос поддерживает `X-Barbar-Catalog-Revision` вместе с `X-Barbar-Role`.
- `/history` и `/report` — история и аналитика для смонтированного экрана/выбранного периода; их клиентские хуки не включены в глобальный опрос.

При неизменной общей revision ответ остатков содержит только `unchanged`, версии и роль; каталог не запрашивается. На сервере в этом случае читаются только метаданные. При обычной продаже версия каталога сохраняется, при реальном изменении каталога/рецептов обновляется в той же транзакции. Для старой базы версия каталога первоначально равна общей revision, без переимпорта записей.

Клиент держит каталог в памяти текущего сеанса вкладки; переходы между разделами и продажи его не перезагружают. При полной перезагрузке страницы каталог загружается заново. Выход/истечение сеанса очищают кеш; переход роли повторно загружает разрешённое представление. Финансовые данные не сохраняются в localStorage/service worker.

## Запись

Обычная продажа возвращает сохранённую продажу, новую revision и только изменённые остатки. Рабочий получает только разрешённые поля продажи и количества без себестоимости. Сервер сохраняет собственные ID идемпотентности, аудит и снимок себестоимости как прежде.

Частичный ответ содержит `baseRevision`; сервер разрешает его только когда revision запроса совпадает с исходным состоянием транзакции. Клиент повторно проверяет исходную revision и версию каталога. Если другое устройство успело изменить данные, сервер возвращает все текущие остатки. Повтор после потерянного ответа не повторяет продажу и возвращает сохранённую запись с полными остатками. Исторические изменения используют совместимый полный путь расчёта на сервере, но возвращают компактный ответ клиенту.

`services/working-state.ts` согласует каталог и остатки. Если правка каталога произошла между двумя чтениями, он повторяет чтение до совпадения версий (не более четырёх попыток), не смешивая разные версии. Сетевые ошибки сохраняют стабильный ID команды для повтора в той же форме. Каталожные массивы владельца сохраняют ссылки при обновлении остатков.

## Проверки и границы

- Тест MongoDB проверяет реальные команды чтения: `state` + `stockBalances`, без коллекций каталога/журнала, и только `state` для неизменного состояния.
- Проверены повтор продажи, устаревшая revision другого устройства, редактирование рецепта, историческая продажа и смена роли.
- Модульные сценарии проверяют согласование разных версий, кеширование каталога и точное совпадение расчёта доступных позиций/мл бокала рабочего с серверным представлением.
- Браузерные сценарии обеих ролей проверяют одну загрузку каталога при продаже и обновлении, перезагрузку после правки и отсутствие фоновых запросов истории/отчётов на странице рецептов.
- На синтетическом каталоге тест фиксирует ответ обычной продажи меньше одной пятой размера каталога; в нём только две изменённые позиции для рецепта из двух ингредиентов. Это проверка объёма ответа, не измерение production latency.

Первое открытие добавляет один запрос каталога. Выигрыш приходится на последующие продажи и обновления. Глобальный опрос остаётся раз в минуту только в видимой вкладке и при фокусе. Транзакции записи всё ещё читают каталог для проверки рецептов и прав учёта; эта задача не меняет их на небезопасные клиентские расчёты. Исторические перерасчёты большого журнала остаются отдельным направлением оптимизации.
