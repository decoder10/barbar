## R01. Разрешение и состав выпуска

- Проверить рабочее дерево, ветку и согласованное назначение. Последний выпуск указывает `decoder10/barbar`, ветку `barbar`, сайт `barbar-cafe.netlify.app`.
- Skill сам по себе не разрешает push или deploy. Прямое поручение пользователя опубликовать изменения разрешает это в пределах поручения; повторно спрашивать то же разрешение не требуется.
- Проверить состав изменений и индекса. Не включать `.env`, реквизиты, локальные данные учёта и тестовые артефакты.
- Исключение `.claude/`, `.agents/`, `.codex/`, `.tandem/` и `.gitignore` относилось к продуктовому выпуску 22 сентября. Это не общий запрет на отдельное согласованное изменение инструкций агентов.

## R02. Проверки перед выпуском по умолчанию

| Проверка | Действующее требование |
| --- | --- |
| `npm run check` | Lint, TypeScript, модульные тесты |
| `npm run build` | Локальная сборка |
| Подходящие Playwright-сценарии | По затронутым сценариям; сервер 4001 запускается отдельно |
| `npm run test:db` | При изменении сохранения данных, в отдельной тестовой MongoDB |
| `npm run test:backup` | Перед выпуском по текущему skill |
| `npm run test:scheduled-backup` | Перед выпуском по текущему skill |
| `npm run benchmark`, `npm run test:load` | Сопоставимые измерения; при изменении запросов сравнить страницы истории и популярные карточки |
| `npm run db:storage` | Отчёт хранилища при доступном Atlas |

После сборки skill требует сверить чанки `react`, `main`, `photo-manifest`, `photo-catalog`, чанки страниц и одинаковые общие preload в `index.html`/`menu.html`. В `dist/barbar` единственным JPG должен быть `bar-hero.jpg`.

**Исключение последнего выпуска:** 22 сентября записано поручение «просто сделай deploy без тестов». Для того этапа повторные автоматические тесты и локальные check-suite исключены; сохранённые результаты обозначены как исторические. Это не удалило проверки из skill и не изменило сборку Netlify. Новое прямое указание пользователя определяет объём следующего выпуска.

## R03. Что запускает Netlify

Конфигурация `netlify.toml`:

```toml
[build]
  command = "npm run build"
  publish = "dist"
  functions = "netlify/functions"

[build.environment]
  NODE_VERSION = "22"
```

Команды `package.json`:

```json
{
  "check": "npm run lint && npm run typecheck && npm test",
  "build": "npm run lint && npm run photos:manifest && tsc -b && vite build"
}
```

**Vitest и Playwright в облачный `build` не входят. Lint и TypeScript входят и могут остановить публикацию.** Указание «без тестов» их не отключает. Изменение облачной сборки требует правки `package.json` или `netlify.toml`.

## R04. Сохранность рабочей базы

- Не сбрасывать данные, не перезаполнять каталог и не менять существующие ID или рецепты ради проверки.
- Проверки записи выполнять в изолированной БД. `dev:production-db` на `localhost:4002` не использовать для тестов; он не запускает миграции и создание начальных пользователей.
- Не создавать на production тестовые продажи и гостевые заявки. Анонимная проверка `/api/guest-order`: GET без кода, ожидается 404 до обращения к БД.
- Индексы подтверждать чтением `appMigrations` и `listIndexes`. Текущие ключи skill: `ledger-indexes-v5`, `audit-indexes-v2`. `db:storage` не подтверждает миграции.
- Миграции могут запускаться при первом подходящем API-запросе после deploy. Не создавать запись в Atlas только ради запуска миграции.
- Изменение секретов, выгрузка рабочей базы и восстановление — отдельные операции; разрешение на deploy кода само по себе их не разрешает. Нерешённые ограничения прежней автоматической проверки — в [облачном аудите](cloud-security.md).

## R05. Подтверждение после публикации

- Подтвердить опубликованный коммит или изменённые ассеты. Один HTTP 200 не доказывает публикацию нового кода.
- Проверить вход, `/`, `/menu`, `/api/menu` и заголовки защиты.
- Проверить 401 на защищённых API без входа, `authenticated: false` на `/api/barbar/auth`.
- Для выпуска заказов проверить чтение доски, существующего заказа, очереди, отчётов и CSV под разрешёнными ролями; не создавать операции и не закрывать смену.
- Выполнить `npm run probe:latency` анонимными GET. Первый ответ замера сам по себе не доказывает холодный старт.
- Записать дату, коммит, результаты и ограничения. Непроверенные облачные настройки, резервирование и push отмечать как неподтверждённые.

## R06. Что можно пересмотреть

Это варианты для выбора владельцем, а не уже принятые изменения:

| Тема | Сейчас | Возможное изменение |
| --- | --- | --- |
| Повтор проверок | Skill требует проверки перед выпуском | Использовать сохранённый результат для неизменившегося кода с указанием версии |
| Объём проверок | `check`, сборка, подходящие e2e; backup-тесты перед выпуском | Выбирать набор по затронутым областям; выделить выпуск только документации |
| Docker и MongoDB | Нужна отдельная тестовая среда; в плане ограничен запуск Docker | Определить, когда запуск разрешён, а когда проверки переносятся |
| Облачная сборка | Lint + манифест + TypeScript + Vite | Явно изменить состав в конфигурации |
| Проверки production | Версия, доступность, права, задержки, отчёт | Зафиксировать обязательный минимум и проверки по изменениям |
| Копии правил | Проектные и персональные skills | Выбрать основной источник и порядок синхронизации |

Для изменения указать R01–R06 и желаемое поведение. Затем обновить действующие источники и памятку. Ограничения среды выполнения и автоматической проверки доступа не отключаются правкой репозитория.
