# Производительность: серверный журнал и отчёты

Текущий API возвращает каталог и материальные остатки из `stockBalances`; продажи, закупки, складские операции и расходы загружаются отдельно страницами по 50 записей. Итоги дня рассчитываются по всему периоду, независимо от открытой страницы. Рабочему выдаются только количества и разрешённые поля.

Обычные продажи, отмена отдельной продажи, закупки, правки каталога/рецептов, пересчёт, списания, заготовки и расходы больше не читают полный журнал. Изменённые записи, балансы и аудит сохраняются одной транзакцией. Перезаписываются только изменённые балансы. Дедупликация использует постоянные ID, а не только последние 1000 команд. Себестоимость хранится без дополнительного округления материализованного остатка.

Отчёты рассчитываются MongoDB aggregation. Кеш до 16 ответов на экземпляр Functions, TTL 30 секунд, ключ содержит revision. Изменение учёта делает старый кеш недействительным; проверка прав выполняется до кеша. Повторные одновременно пришедшие запросы используют один расчёт. Это кеш конкретного экземпляра, не обещание общего кеша между всеми Functions.

## Нагрузочная проверка

`npm run test:load` создаёт и удаляет **только отдельную локальную тестовую БД**. 59 позиций, 50 000 накопленных синтетических продаж; два экземпляра репозитория. Следующие значения получены 14 сентября 2026 на локальном MongoDB replica set и этом компьютере. Обработчики вызываются через Request/Response внутри процесса с тестовым провайдером сессии; это не сетевой HTTP-бенчмарк. Сетевая задержка Atlas, холодный запуск Netlify и реальная многопользовательская нагрузка в эти цифры не входят.

| Проверка                                       | Запросы / параллельность | p50       | p95        |
| ---------------------------------------------- | ------------------------ | --------- | ---------- |
| Рабочий каталог и остатки                      | 60 / 10                  | 11,43 мс  | 18,02 мс   |
| Первая страница истории, холодный запрос + кеш | 12 / 4                   | 1,37 мс   | 131,26 мс  |
| Отчёт без кеша                                 | 1 / 1                    | 259,52 мс | один замер |
| Отчёт из кеша                                  | 40 / 8                   | 0,88 мс   | 1,78 мс    |
| Новые продажи                                  | 30 / 6                   | 6,71 мс   | 256,88 мс  |
| Повтор тех же команд                           | 30 / 6                   | 7,21 мс   | 10,23 мс   |

Полный журнал: **11 854 753 байта**. Рабочий ответ: **39 764 байта**, примерно в **298 раз меньше**. Страница истории: 12 209 байт. Индексированная выборка страницы читает 51 документ, а не 50 000. Агрегаты всего периода всё ещё обрабатывают продажи периода на сервере — пагинация не делает вычисление месячных итогов константным.

После 30 параллельных записей и 30 повторов подтверждены: ровно 50 030 продаж, 30 событий аудита, остаток 949 700 мл, совпадение стоимости полного и рабочего представлений. Отдельный тест проверяет конкурентную продажу последнего остатка и откат балансов/аудита при ошибке записи.

## Практические пределы

- Первая миграция старой БД один раз читает историю для построения балансов. Каталог и пользовательские рецепты не пересоздаются. Для крупного старого журнала предварительно нужна копия и проверка миграции отдельно.
- Восстановление, архивация, исправление старой закупки и задним числом добавляемые продажи используют полный журнал для проверки исторических ограничений. Это редкие операции, их дальнейшее масштабирование потребует отдельного проекта. Обычная запись продажи от них не зависит.
- Браузерная полная копия/восстановление ограничены 3 МБ. Для большой базы используется зашифрованная локальная копия. Большие атомарные импорты могут превысить кеш/лимит транзакции: нагрузочная история подготавливалась пакетами, как уже накопленный журнал.
- Один документ revision сериализует изменения склада: это защищает от перепродажи, но ограничивает максимальную конкурентную запись. Для нагрузки сети заведений потребуется разбиение по заведению/складу, а не просто увеличение пула.
- Нагрузочные записи в рабочую базу или продакшен-сайт не выполнялись. Производственные latency/cold starts нужно наблюдать после согласованного выпуска.

## Живой Network перед исправлением задержек (17:03 Ереван)

Проверена открытая авторизованная вкладка production, релиз `9b78021`, Chrome Network с отключённым кешем. В текущем журнале: auth 385 мс, остатки 643 мс, каталог 865 мс (4,8 КБ сжатых / 47,2 КБ JSON), история продаж 468 мс. В Timing каталога ожидание сервера 858,65 мс, скачивание 5,99 мс. Предыдущий пользовательский снимок показывал 5,40 с для каталога. Это единичные наблюдения, не p95 или доказательство причины холодного запуска.

По коду найдены и сокращены повторные операции подготовки пользователей/индексов при холодном запуске, лишние MongoClient и последовательное ожидание каталога после остатков. Добавлен Server-Timing для повторного замера после выпуска. Каталог пока целиком остаётся необходимым справочником для клиентских расчётов; серверная пагинация карточек — незавершённая отдельная работа, не следует выдавать локальный AutoReveal за серверную пагинацию.

После публикации `e91fa8e` подтверждён JS `/assets/index-DhL0m4JM.js`, анонимные основной API и каталог вернули 401. Первый авторизованный каталог: 3,10 с, Server-Timing auth 953 мс/data 729,3 мс. Повтор: auth-запрос 692 мс, остатки 727 мс, каталог 924 мс, история 807 мс. В повторном каталоге auth 83,2 мс/data 510,9 мс, скачивание 6,62 мс. Это всё ещё переменные задержки; устойчивого SLA по этим двум наблюдениям нет. Добавлен отдельный серверный кеш каталога по revision, чтобы сокращать оставшиеся последовательные чтения базы.
