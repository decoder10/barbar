# Индексы под запросы Barbar Cafe

Схема индексов учёта и аудита: `netlify/lib/database/indexes.ts`. Индексы, добавленные после появления реестра миграций, описаны шагами `2026-…` в `netlify/lib/database/registry.ts` (правила: `docs/database-migrations.md`). Проверки запросов выполняются на отдельной локальной MongoDB. Рабочая Atlas в этом этапе не изменялась.

## Как выбирались

Проверены `find`, `findOne`, `$match`, `distinct`, сортировки, курсоры страниц, `$lookup` и фильтры записи. Индексируется форма запроса, а не каждое поле фильтра. Для составных индексов учитываются равенство, сортировка и диапазон — [MongoDB ESR](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/). Польза проверяется через `explain('executionStats')`, без принудительного `hint`, по прочитанным документам/ключам и отсутствию блокирующей сортировки — [MongoDB explain](https://www.mongodb.com/docs/manual/tutorial/analyze-query-plan/).

| Запрос                                             | Индекс                                                                            | Решение                                                                                                 |
| -------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Пользователь, сессия, состояние, операция по `_id` | Встроенный `_id_`                                                                 | Второй индекс не нужен                                                                                  |
| Вход по username + active                          | Уникальный `username`                                                             | Найден максимум один пользователь, отдельный active не нужен                                            |
| Отзыв сеансов / срок жизни                         | `sessions.userId`, TTL `expiresAt`                                                | Сохранены                                                                                               |
| История продаж, движений и сбросов: дата + курсор  | `date DESC, createdAt DESC, id DESC`                                              | Сохранён, обслуживает также диапазон дат                                                                |
| История закупок и расходов                         | `date DESC, id DESC`                                                              | Сохранён                                                                                                |
| Полный экспорт и прежний порядок журнала           | `_order`                                                                          | Сохранён для существующего сценария                                                                     |
| Связь закупок со складом в отчёте                  | Уникальный `alcohol.id`                                                           | Сохранён для `$lookup`                                                                                  |
| Аудит без фильтра / по сотруднику / по действию    | Три существующих индекса с `createdAt DESC, id DESC`                              | Сохранены: каждый поддерживает свою сортировку                                                          |
| Аудит одновременно по сотруднику и действию        | `actor.id, action, createdAt DESC, id DESC`                                       | Добавлен                                                                                                |
| Количество отмен в периоде                         | `date`, только `voided: true`                                                     | Добавлен частичный индекс; действующие продажи не занимают место в нём                                  |
| Все виды произведённых заготовок                   | `kind, outputId`, только `kind: prepare`                                          | Добавлен частичный индекс для `DISTINCT_SCAN`                                                           |
| Списания конкретной партии                         | `stockMovements.batchId`, только с `batchId`                                      | `ledger-indexes-v5`: частичный индекс, обычные движения не занимают место                               |
| Продажи, списавшие конкретную партию               | `sales.ingredients.batches.id` (`sale_batches`)                                   | `ledger-indexes-v5`: разреженный индекс; исправление выхода отказывает партии, из которой уже продавали |
| Последние оплаченные чеки сотрудника и стола       | `orders {openedBy.id, status, openedAt DESC}`, `{tableId, status, openedAt DESC}` | `ledger-indexes-v5`: повтор заказа без сканирования                                                     |
| История цен                                        | `priceChanges {productId, createdAt DESC}`, `{createdAt DESC}`                    | `ledger-indexes-v5`; поставщики — `suppliers.name`                                                      |
| Страница истории цен: вся / по товару              | `priceChanges {createdAt DESC, id DESC}`, `{productId, createdAt DESC, id DESC}`  | `2026-09-25-price-history-indexes`: сортировка запроса включает `id`, индексы v5 её не покрывали        |
| Лента уведомлений: 50 новых событий каждой очереди | `{createdAt DESC}` в `stockAlertEvents`, `purchaseEvents`, `guestEvents`          | `2026-09-25-notification-feed-indexes`; TTL-индексы `expiresAt` остаются для удаления                   |

Не добавлялись отдельные индексы на цены, количество, названия, `users.active/role`, каждое поле ингредиента и обычные неотменённые расходы: текущие запросы либо работают с малым справочником, либо читают весь отобранный период, либо уже используют подходящий индекс. Полная агрегация продаж за месяц всё равно должна прочитать продажи этого месяца; индекс не заменяет агрегацию.

## Удаление прежних индексов

После успешного создания замен удаляются только пять точных прежних неуникальных индексов приложения:

- `sales.date_1_createdAt_1`;
- `sales.date_-1_id_-1`;
- `purchases.date_1_alcoholId_1`;
- `stockResets.date_-1_id_-1`;
- `stockMovements.date_-1_id_-1`.

Текущий код не сортирует продажи/движения/сбросы только по date/id: он использует полную хронологию date/createdAt/id. Сортировка по возрастанию date/createdAt также поддерживается обратным проходом существующего индекса. Фильтра закупок по alcoholId в MongoDB сейчас нет; диапазон дат покрывается индексом пагинации.

Миграция идемпотентна, переносит конкурентный запуск и не меняет документы. Индексы с другими именами/ключами, уникальностью, TTL, partial/sparse или collation не удаляются. Итог: три необходимых индекса добавлены, пять лишних убраны, всего на два меньше. Индексы пользователей и сессий остаются в модуле авторизации.

## Замер 14.09.2026

По 30 000 синтетических документов в каждой проверяемой коллекции; 20 сотрудников, 10 действий, 300 отмен, 1 000 приготовлений с 7 разными выходами.

| Запрос                                | До: документы | После: документы | После: ключи |
| ------------------------------------- | ------------: | ---------------: | -----------: |
| Аудит сотрудник + действие, 51 запись |           506 |               51 |           51 |
| Подсчёт отменённых продаж             |        30 000 |                0 |          300 |
| Уникальные выходы заготовок           |        30 000 |                0 |            7 |

Проверены неизменность результатов, глубокая страница после 15 000-й записи без полного просмотра/блокирующей сортировки, обратная сортировка и сохранение пользовательских и уникальных индексов. В `scripts/db/load-test.mjs` explain теперь повторяет фактическую сортировку истории, включая createdAt.

Команда `npm run test:db` включает тесты индексов. Это воспроизводимый локальный замер работы планировщика, а не обещание конкретного времени ответа Netlify/Atlas. Индексы применятся к существующей рабочей базе при инициализации нового кода после публикации; отдельный ручной ввод индексов в Atlas не требуется.

После изменений прошли `npm run check` (79 тестов без подключённой БД), `npm run test:db` (20 проверок), production build и форматирование. Повторная нагрузка на 50 000 продаж: страница истории прочитала ровно 51 документ/51 ключ, проверены 30 параллельных продаж, повторы, остаток и оценка запасов. Время одного холодного отчёта составило 221 мс локально; это отдельный запуск без гарантии такого же времени на рабочем сервере.

## Горячие запросы API, 25.09.2026

`netlify/lib/database/hot-paths.test.ts` (входит в `npm run test:db`) вызывает настоящие функции API на временной локальной базе: доску открытых заказов, отчёт смен за месяц, повтор заказа («мои» и по столу), ожидающие гостевые заявки, ленту уведомлений владельца и сотрудника, журнал аудита (три фильтра), историю цен (всю и по товару) и две страницы истории продаж. Каждый запрос к растущей коллекции перехватывается через мониторинг команд драйвера и повторяется как `explain('executionStats')` в том виде, в котором его отправил код. Тест требует:

- ни одного `COLLSCAN` в `orders`, `sales`, `shifts`, `auditEvents`, `priceChanges`, `guestRequests`, очередях уведомлений и журналах учёта;
- для `find`: без блокирующей сортировки и не больше чем `2 × возвращено + 2` прочитанных документов;
- лента: ровно 50 документов на очередь по индексу `createdAt_-1`, а состав и порядок ленты совпадают с независимым расчётом по всем событиям, для владельца и для сотрудника.

Данные синтетические: 12 000 заказов за 240 дней, 24 000 строк чеков, 3 000 изменений цен, 20 000 событий аудита, 3 000 гостевых заявок, по 2 000 событий в каждой очереди. Сырые результаты: `docs/perf/2026-09-25-hot-paths.json`.

| Запрос                            | До: план, документы → строк           | После: план, документы → строк                   |
| --------------------------------- | ------------------------------------- | ------------------------------------------------ |
| Лента: предупреждения об остатках | COLLSCAN + SORT, 2 000 → 50           | IXSCAN `createdAt_-1`, 50 → 50                   |
| Лента: закупки (владелец)         | COLLSCAN + SORT, 2 000 → 50           | IXSCAN `createdAt_-1`, 50 → 50                   |
| Лента: гостевые заявки            | IXSCAN `expiresAt_1` + SORT, 800 → 50 | IXSCAN `createdAt_-1`, 50 → 50                   |
| История цен, первая страница      | COLLSCAN + SORT, 3 000 → 30           | IXSCAN `createdAt_-1_id_-1`, 30 → 30             |
| История цен одного товара         | IXSCAN + SORT, 150 → 30               | IXSCAN `productId_1_createdAt_-1_id_-1`, 30 → 30 |

Остальные проверенные запросы уже шли по индексам и не изменились: открытые заказы (6 → 6), строки чеков по `orderId` (`order_lines`), заказы и смены периода (`businessDay_1`), повтор заказа (10 → 10), аудит (51 → 51), первая страница истории продаж (51 → 51).

Новые индексы строятся шагами `2026-09-25-notification-feed-indexes` и `2026-09-25-price-history-indexes` в конце `schemaMigrations`. Они только создают индексы и документы не трогают. На рабочей базе оба шага выполнятся один раз при первом запросе после публикации; прежние шаги не перезапускаются (`migrations.test.ts`). Очереди уведомлений ограничены TTL, изменения цен редки, поэтому построение индексов и лишняя запись при вставке малы. Индексы v5 `priceChanges.createdAt_-1` и `productId_1_createdAt_-1` теперь стали префиксами новых. Они оставлены: удалять индекс можно только отдельным шагом после проверки (см. правила миграций), а выигрыш от удаления здесь незначителен.

Осознанно оставлено без индекса:

- **Ожидающие гостевые заявки** сортируются в памяти, но читаются только живые ожидающие заявки (30 → 30). Их число ограничено лимитом заявок на стол. Индекс «сортировка перед диапазоном» заставил бы проходить и просроченные неотвеченные заявки.
- **Вторая страница истории продаж** прочитала 101 ключ ради 51 строки: планировщик один раз проходит ключи уже показанной страницы. Глубокие страницы проверяет `indexes.test.ts` (не больше 60 документов после 15 000-й записи). Сузить это можно в `queries/history.ts`, добавив к фильтру курсора верхнюю границу `date ≤ дата курсора`. Результат не изменится, но в этой части это не сделано.
- **Агрегации по периоду** (группы истории продаж, продажи вокруг изменений цены) читают все продажи периода по индексу даты. Это суть расчёта, и результат кэшируется до следующей записи (`queries/cache.ts`). В истории цен также читаются все изменения товаров со страницы (3 000 при 20 товарах): это нужно, чтобы найти соседние изменения. Индекс по товару в `sales` удорожил бы каждую продажу ради редкого отчёта владельца.
- **Команды записи** (`execute` в `barbar-mongo.ts`) при каждой команде читают все смены целиком (`shifts.find({})`, одна строка на рабочий день). Индексом это не лечится: нужно загружать только смены затронутых дней и команды закрытия. Это изменение логики записи, в эту часть оно не входит.
