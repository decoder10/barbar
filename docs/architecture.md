# Архитектура Barbar Cafe

## Границы модулей

- `src/barbar/domain`: типы, команды и чистые расчёты учёта. `model.ts` — единая проверка и применение команд; `inventory-calculations.ts` — производная модель для быстрого чтения; `reports` — аналитика, периоды и рекомендации цен.
- `src/barbar/features`: формы и составные компоненты по направлениям `auth`, `catalog`, `inventory`, `recipes`, `sales`, `reports`, `operations`. Формы закупки, исправления закупки, сброса остатков, продажи и рецепта вынесены из страниц.
- `src/barbar/ui`: общие поля, модалка, кнопка отправки, показатели, заголовки и экспорт. Импорты идут из конкретного модуля; общего файла реэкспортов `components.tsx` нет.
- `src/barbar/pages`: маршруты и композиция сценариев. Страницы владельца и рабочего используют разные API-представления.
- `src/barbar/services`: HTTP-клиент с таймаутом и объединением одновременных GET. Мутации никогда не объединяются.
- `src/barbar/app`: маршрутизация и сборка приложения. `providers/BarProvider.tsx` управляет авторизацией, состоянием сервера, revision и отправкой команд. Данные обновляются после успешной записи либо изменения revision.
- `src/barbar/domain/identity`: общие для клиента и сервера типы профиля, ролей и предпочтений.
- `src/barbar/domain/catalog`: миграция бутылочного каталога и метаданные старых номеров изображений, которые используются в валидации сохранённых позиций.
- `src/barbar/presentation`: настройки отображения. `SettingsProvider.tsx` применяет предпочтения, `PreferenceControls.tsx` содержит переключатели, `settings-context.ts` описывает их контракт. В `currency` находится форматирование валюты, в `i18n` — переводы. Учёт всегда в AMD; язык, тема и отображаемая валюта не изменяют операции.
- `src/barbar/features/catalog/media`: выбор фотографий и генерируемый манифест ресурсов. Изображения привязаны к существующим товарам без изменения рецептов и учёта.
- Модульные тесты находятся в `__tests__` рядом с проверяемой областью; браузерные сценарии остаются в корневом `tests`.
- `presentation/use-session-filter.ts` и `services/session-filters.ts` сохраняют фильтры, поиск, сортировку, вид склада и период отчётов в `sessionStorage`. Ключи разделены по пользователю, роли и маршруту. Выход и новый вход очищают только эти ключи; другие данные вкладки не затрагиваются. Формы операций не сохраняются. Выбор текущего барного дня хранится как «текущий», поэтому граница 06:00 продолжает работать.
- `src/barbar/styles`: SCSS с единой точкой входа `index.scss`, семантическими CSS-переменными в `_tokens.scss`, миксинами и отдельными файлами разделов. Темы меняются через `data-theme` корневого элемента.
- `netlify/lib`: авторизация, серверные права, обработчики, репозитории и интеграция ЦБ Армении. Тонкие Functions и локальный сервер используют одни обработчики.
- `public/barbar/photos`: оптимизированные изображения и сведения об источниках. `scripts/photo-manifest.mjs` формирует компактный клиентский манифест (авторы списком, варианты как `<ширина>.<хеш>`; раскрывает `photo-catalog.ts`) с версией URL и страницу авторства. Свои фото владельца хранятся вне репозитория (Netlify Blobs), в манифест не входят.

## Обратная связь и блокировка действий

- `ui/use-async-task.ts`: общий синхронный lock через ref, текст текущего действия и освобождение в `finally`. Повторное событие до React-render не запускает второй запрос.
- `BarProvider.perform` объединяет запись учёта, изменение пользователей, настройки, вход/выход и чтение файла восстановления. `run` сохраняет прежний command ID для безопасного повтора после неопределённого сетевого результата.
- `ui/loading.tsx`: переиспользуемые `BusyButton` и `LoadingStatus`, `aria-busy`, статус для скринридера и поддержка reduced motion.
- `Modal` блокирует все поля и кнопки через fieldset, а также Escape/закрытие, пока действие выполняется. `styles/_loading.scss` сбрасывает стандартные рамки и отступы fieldset. После ошибки форма остаётся открытой с введёнными значениями.
- Во время записи навигация и основной экран `inert`; текущий диалог остаётся доступным для чтения статуса. Первичная загрузка не показывает незагруженный рабочий каталог. Обновление данных имеет отдельное состояние, блокирующее повторное обновление.
- Общий `Brand` ведёт на продажи `/`; на телефоне переход закрывает меню. При сохранении навигация заблокирована вместе с боковой панелью.

## Полный экран продаж

`features/sales/SalesFullscreen.tsx` — общий переключатель для владельца и рабочего, подключённый через общий `SalesDayToolbar.tsx` на страницах продаж обеих ролей. Класс `sales-fullscreen` скрывает навигацию, метрики и декоративные блоки; фильтры, каталог, дневной журнал и формы остаются на месте без перемонтирования. Fullscreen API дополняется обычным режимом без панелей для мобильных/встроенных браузеров. Выход через кнопку, браузер или Escape синхронизирует интерфейс; уход со страницы снимает режим. Стили изолированы в `_sales-fullscreen.scss`.

## Прокрутка каталога

`ui/auto-reveal.tsx` раскрывает локально загруженные карточки порциями по 24 через `IntersectionObserver`, за 400 px до конца списка. Используется в продажах и рецептах обеих ролей; не делает запросов к API. Наблюдатель отключается после раскрытия и при размонтировании. Кнопка остаётся доступной с клавиатуры и как резервный способ при отсутствии API наблюдения. Поиск и категории возвращают начальную порцию. Серверная пагинация журнала операций остаётся отдельной.

## Предупреждения об остатках

`domain/notifications` содержит общие пороги и сравнение остатков. `features/notifications` показывает предупреждения и управляет разрешённой подпиской устройства. `netlify/lib/notifications` записывает транзакционную очередь, проверяет подписки/сеансы и отправляет Web Push после сохранения. `public/barbar-sw.js` принимает push и открывает склад; кеширования рабочих данных нет. [Настройка и ограничения](stock-notifications.md).

## Контракты данных

Команда получает стабильный ID, проверяется на сервере и записывается в MongoDB транзакцией. Продажа хранит снимок списания и себестоимости; отмена использует этот снимок. Revision защищает от устаревших изменений. Закупки и изменения рецепта не переписывают прошлую себестоимость продаж.

Рабочий получает только разрешённые поля через `barbar-access.ts`. Финансовые поля исключаются на сервере, а не скрываются стилями. Роль читается из действующего пользователя при обращении к API. Настройки профиля изменяются только для текущего пользователя.

Смена начинается в 06:00 по Еревану. У бутылки отдельно хранятся объём бутылки, стандартная порция и выбранный объём продажи. Старые позиции без связанного склада требуют настройки перед списанием.

- `npm run build`: lint, манифест фотографий, типы и production-сборка.
- `npm run test:e2e`: сценарии интерфейса, права, настройки, мобильная раскладка.
- `npm run test:db`: проверки отдельной тестовой базы MongoDB; рабочая база не очищается.

## Разделённая синхронизация

`domain/sync/contracts.ts` описывает отдельные ответы каталога и остатков; `services/catalog-client.ts` согласует отдельные ответы alcohol/cocktails, `services/working-state.ts` согласует версии каталога и остатков и применяет частичные ответы. `netlify/lib/barbar-sync.ts` формирует разрешённые представления и ответ команды. Каталог кешируется в памяти сеанса, его версия меняется только при правке. Основной GET читает только метаданные и балансы; продажа возвращает запись и изменённые остатки. Старые вкладки поддерживаются заголовком версии протокола. [Контракт, проверки и ограничения](api-sync.md).

Чтения отчёта, истории и партий идут через `snapshotRead(data, path)` из `services/api-client.ts`. Результат запоминается для текущего снимка данных и сбрасывается, когда после записи или обновления журнала приходит новый снимок. Благодаря этому два хука с одинаковым отчётом («Отчёты» и «Прогноз закупок») и экран, который монтируется заново после загрузки, делают один запрос. Одновременные одинаковые GET по-прежнему объединяет `api()`. Профиль базы (`/api/barbar/environment`, только в разработке) читается один раз за загрузку страницы.

## Серверные остатки и история

- `netlify/lib/database/indexes.ts`: индексы учёта/аудита под формы запросов и идемпотентное удаление точных устаревших неуникальных индексов приложения. Обоснование и explain — `docs/database-indexes.md`.

- `netlify/lib/barbar-working.ts`: `stockBalances`, компактное рабочее представление. Это производная модель, её нельзя принимать как файл восстановления.
- `netlify/lib/barbar-mongo.ts`: транзакционные текущие операции и совместимый полный репозиторий для восстановления/исторических правок. Однократная миграция строит балансы из сохранённого журнала.
- `netlify/lib/queries`: индексированная пагинация, серверные агрегаты и ограниченный кеш по revision. Functions `/history` и `/report` используют те же обработчики, что локальный Node-сервер.
- `netlify/lib/audit`: только серверный автор события, ограниченные поля и описание операции. Событие и операция сохраняются атомарно. Журнал доступен владельцу, клиентских команд редактирования/удаления аудита нет.
- `domain/operations.ts`: инвентаризация, списания, заготовки и расходы. Подготовка партии переносит стоимость ингредиентов в выход; сумма изменения стоимости запасов равна нулю. Потери и обычные расходы учитываются отдельно.
- `domain/reports/purchasing.ts`: одна формула закупочного прогноза для локальных данных и серверных агрегатов. `aggregated.ts` формирует показатели и рекомендации по компактным группам.
- `features/sales/use-history.ts`, `features/reports/use-server-report.ts`: загрузка страниц и отчётов; `ui/pagination.tsx` — общая навигация. Страница истории не является источником итогов всего периода.
- `barbar-users.ts`: изменение доступа увеличивает `authVersion` и отзывает сессии; проверка версии защищает также от входа, который начался одновременно со сбросом пароля. Изменения владельцев сериализуются, последний активный владелец защищён.
- `scripts/db`: локальные зашифрованные копии, восстановление в отдельную БД и воспроизводимые нагрузочные/восстановительные проверки. Рабочие секреты сюда не входят.

## Общий интерфейс ролей

Оболочка и `PreferenceControls` доступны владельцу и рабочему: язык, тема и валюта сохраняются в профиле. Рабочий видит продажные цены и дневные суммы в выбранной валюте; курсы загружаются для любой роли при выборе валюты, отличной от AMD. Учёт остаётся в AMD.

`CatalogCard` задаёт единую разметку карточек продаж и рецептов; отдельные адаптеры подают фотографию, текст и разрешённый подвал. `InventoryProduct`, `InventoryStock` и `InventoryCategories` используются обеими страницами склада. Таблицы/сетки и подсветка отсутствия используют одни классы `inventory-table` / `inventory-shortage` и токены темы; старых стилей склада рабочего нет.

С 15.09.2026 рабочий получает те же компоненты, что владелец. Карточки продаж и рецептов: `CocktailCard`, `AlcoholCard`, общие `compositionText` и `stockPill`. Также общие окно продажи `SaleDialog`, строки рецепта `IngredientRows`, выбор фото `PhotoPicker`, нехватка `RecipeShortages` / `ShortageNote` и расчёт `domain/shortages.ts`. Ограничения роли реализованы так: данные, которые рабочий не должен видеть, просто не передаются в компонент (`hidePrice`, без `cost` и `costLines`). Отдельной вёрстки для рабочего нет. `StaffProduct.serving` передаётся, чтобы фото совпадали с карточкой владельца. Чек рабочего — те же строки `receipt-line`, но сгруппированные по позиции, без отмены и выгрузки.

Группы склада, флаги категорий меню, тексты гостевого меню, миграции каталога и готовые значения читаются из `src/barbar/config/*.json`, см. [configuration.md](configuration.md).

`SalesDayToolbar` объединяет полный экран, создание коктейля и календарь в одну строку с горизонтальным скроллом на узком экране. Рабочий видит продажные цены, итог формы и дневную сводку количества/выручки без списка отдельных операций и его пагинации. Суммы сводки берутся из сохранённых продаж, а не из текущих цен каталога. Себестоимость, закупочные цены, прибыль, отчёты, аудит и административные изменения доступны только владельцу. Продажи, рецепты, фильтры, сортировка, сетка/список и уведомления сохраняются у рабочего.

Проверка общего интерфейса (14.09.2026): `npm run check` — 93 модульных теста, lint и типы; `npm run build`; Playwright — 51 сценарий. Дополнительно проверены сохранение настроек рабочего после refresh, отсутствие закупочных цен, себестоимости и административных кнопок, равенство стилей склада обеих ролей в light/dark и отсутствие горизонтального переполнения при ширинах 390/768/1440 px. Настройки и операции в браузерных сценариях используют тестовые данные; рабочие профили и учёт при выпуске не изменяются.

Левое меню сворачивается до панели шириной 76 px через общую кнопку в шапке. `useSessionFilter` принимает необязательную область `scope`: состояние панели записывается в области `workspace`, поэтому сохраняется между маршрутами и после refresh в рамках сеанса, отдельно для пользователя/роли. На экранах до 760 px действует прежнее полное выдвижное меню. Полный экран продаж временно скрывает панель, сохраняя выбор сворачивания. Стили — `_sidebar-collapse.scss`; ширина рабочего пространства связана с `--sidebar-width`.

Проверка сворачивания меню и продажных сумм рабочего (14.09.2026): lint/типы и 93 модульных теста, 31 проверка в изолированной MongoDB, production build и 53 браузерных сценария. Проверены единая строка действий, сворачивание для обеих ролей, сохранение состояния, мобильное меню, суммы бокалов с выбранным объёмом и запрет передачи закупочных цен/себестоимости рабочему.

## Столы, заказы и оплата (22.09.2026)

Проект и принятые решения — [orders-design.md](orders-design.md). Первый этап опубликован 22.09.2026 (`ede72d3`, [проверка выпуска](release-2026-09-22-orders.md)): столы, чеки, оплата, доска столов; заказ гостя по QR и закрытие смены — следующие этапы.

- **Модель.** Заказ (`Order`) не хранит строки: строка чека — обычная `Sale` с полем `orderId`. Остатки, снимок себестоимости, отмены, история, отчёты и уведомления работают на продажах без изменений; заказ добавляет стол, статус, кто открыл/закрыл, оплату и итог. Столы (`BarTable`) — коллекция с кодом для будущей QR-ссылки. Обе коллекции входят в `ledgerCollections`, резервную копию и `validateData`.
- **Команды.** `saveTable`, `removeTable`, `void` — владелец. `openOrder`, `sale` с `orderId`, `payOrder`, `cancelOrder` и `removeLine` — сотрудник и владелец; `removeLine` снимает строку только с открытого заказа, поэтому домен не знает ролей (`CommandContext` несёт только исполнителя). `payOrder` требует `expectedTotal`, равный сумме активных строк, и способы из `config/payment-methods.json`; сумма платежей равна итогу. Заказ создаётся с первой позицией: маршрут `/orders/new` — черновик без записи.
- **Сервер.** `execute` подгружает в рабочую копию только нужный заказ, его строки (с возвратом их списаний в баланс, как для `void`) и столы; повтор команды идемпотентен через `auditEvents`. `GET /api/barbar/orders` (`routes/orders.ts`) отдаёт столы, открытые заказы и их активные строки; сотруднику — через `staffData`. Индексы: `sales.orderId` (частичный), `orders {status, businessDay, openedAt}`, `orders {tableId, status}`, `tables.code` уникальный; ключ миграции `ledger-indexes-v3`. Удаление стола — единственная команда, которая уменьшает коллекцию; прошлые заказы сохраняют его id.
- **Экраны.** `/` — доска столов (`pages/Tables.tsx`), одна для обеих ролей; `/orders/:orderId` — экран заказа с общим каталогом `features/sales/SalesCatalog.tsx` (тот же, что на «Продажах») и чеком `features/orders/OrderReceipt.tsx`; оплата — `features/orders/PaymentSheet.tsx` (наличные со сдачей, карта, перевод, Idram, разделение поровну или произвольными суммами). Касание карточки всегда открывает окно продажи `SaleForm`/`StaffSaleForm` с количеством; окна отдают значение через `onSubmit`, а экран заказа сам создаёт заказ с первой строкой (`run` возвращает записанный ID) — закрытое окно не оставляет пустого заказа; «+» в чеке повторяет строку, «−» убирает последнюю. Владелец настраивает столы в модалке `TablesEditor`. «Продажи» (`/sales`) — журнал всего дня: касание карточки там и кнопка «Быстрая продажа» открывают заказ без стола (`/orders/new?add=kind:id`), отдельных мгновенных продаж больше нет.
- **Полный экран.** Режим хранится в `presentation/fullscreen-store.ts`, класс и Fullscreen API применяет `FullscreenMode` в оболочке, поэтому он сохраняется между доской, заказом и «Продажами»; панель `SalesFullscreen` есть на всех трёх экранах, из «Продаж» в полном экране есть ссылка «Столы».

## Приоритет 2: избранное, партии, закупки, сравнение, цены (выпуск 24 сентября)

- **Избранное и повтор заказа (T06).** Личное избранное — поле `favorites` профиля (`kind:productId`, до 60, `domain/favorites.ts`); меняется `POST /api/barbar/favorites` с `{favorites}` (`routes/favorites.ts`, основной API; лимитированный маршрут входа не используется) и пишет только это поле, не трогая настройки и доступ. Избранное заведения — флаг `favorite` у меню и розлива; ставит только владелец командой `setFavorite`, сотрудник получает его в `StaffProduct.favorite`. Звёздочка и булавка — отдельные кнопки рядом с карточкой (`features/sales/FavoriteButtons.tsx`, `.card-wrap`), вкладка «Избранное» в `SalesCatalog` строится из известных клиенту ключей. Повтор: `GET /api/barbar/orders/recent?scope=mine|table` (свои чеки — по сессии, не по параметру), чистая функция `domain/orders/repeat.ts` подставляет текущие цену и наличие (снятые и закончившиеся строки исключены), окно `RepeatOrderSheet`. Сохранение — одна команда `addLines {orderId | tableId, lines, expectedTotal}`: открывает чек стола при необходимости (его id — id команды), строки получают id `<команда>_<n>`; несовпадение итога отклоняет набор целиком. Повтор той же команды не пишет ничего (`operations` в полном режиме, `auditEvents` на сервере).
- **Стоимость партии (T07).** `prepare` принимает `plannedQuantity` (план); фактический выход — `quantity`; потери = план − факт. Порция, ингредиент другой заготовки и обычное списание берут стоимость через `domain/batches.ts` `batchConsumption`: сначала остаток, не разнесённый по партиям, по остаточной стоимости, затем партии FEFO по стоимости единицы; стоимость не больше стоимости баланса, а обнуление забирает её целиком. Снимок `batches: [{id, ml, cost}]` лежит в ингредиенте продажи, поэтому отмена возвращает ровно сохранённые количество и стоимость. Позиции без партий, прежние продажи и недостача при инвентаризации остаются по средней стоимости. `writeoff.batchId` списывает конкретную партию по её стоимости единицы, но не дороже стоимости баланса (обнуление забирает её целиком, баланс и разнесение по партиям могут расходиться), и уменьшает её ёмкость; `correctBatchYield` меняет факт только нетронутой партии: по FEFO она целая, и ни одна действующая продажа не ссылается на неё в `ingredients.batches` (сервер ищет такую продажу по индексу `sale_batches`); стоимость партии сохраняется. **Строки партий на сервере нельзя загружать в `stockMovements`** — остатки в рабочей копии уже включают их: `netlify/lib/batch-sources.ts` кладёт их в непостоянное `BarData.batchSources` только для затронутых заготовок (`commandStockIds`). Исправление выхода загружает партию как отменяемую продажу: возвращает её строки в баланс и применяет новый выход. Поле, которое команда убрала, удаляется из документа (`$unset` в записи `execute`).
- **Закупки (T08).** Коллекция `suppliers` (`saveSupplier`, `removeSupplier` — снимает ссылку у позиций); у позиции необязательные `supplierId`, `leadDays`, `safetyDays`, `safetyStock`, сотруднику они не передаются. `forecastFromUsage`: расход на рабочий день в наличии × доля рабочих дней периода; срок поставки — позиция → поставщик → значение формы; страховой запас = `safetyStock` + ожидаемый расход × (`safetyDays` ?? резерв формы). Каждая строка возвращает срок, источник, запас, доли и итог; `domain/reports/forecast-explanation.ts` пишет формулу. Не заданное значение показывается как «не задано», данные владельца не выдуманы.
- **Сравнение периодов (T09).** `GET /api/barbar/report/compare?from&to&baseFrom&baseTo` (только владелец, один `$facet` на период внутри snapshot-транзакции, кеш по revision): позиции, дни недели, часы (Ереван; продажи, внесённые после своего дня, — «время неизвестно»), категории. `domain/reports/compare.ts`: изменение выручки = объём + ассортимент + цена + новые/ушедшие позиции, сумма равна разнице до копейки; итоги — те же группы, что в отчёте. Порции розлива считаются стандартными порциями. Сравнение не доказывает причину.
- **История цен (T10).** Коллекция `priceChanges` пишется в транзакции команды `alcohol`/`cocktail` только когда цена существующей позиции изменилась (меню — `price`, розлив — `pricePerLiter`), с автором. `GET /api/barbar/prices` (только владелец): для каждого изменения окна до/после одинаковой длины (до 14 дней, без дня изменения, не дальше соседних изменений и сегодняшнего дня) с продажами, валовой прибылью, средней ценой и наличием по ингредиентам (`domain/reports/price-history.ts`). «История ведётся с» — дата маркера `ledger-indexes-v5`; более ранние цены не сохранялись. Цены сами не меняются.
