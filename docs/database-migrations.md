# Миграции базы Barbar Cafe

Любое изменение структуры базы (индексы, коллекции, поля документов, каталог по умолчанию) делается версионированной миграцией. Ручные правки коллекций в рабочей базе не делаются.

## Как устроено

- `netlify/lib/database/migrations.ts` — движок. `runMigrations(db, list)` выполняет по порядку только шаги без отметки в `appMigrations` и останавливается на первой ошибке. `oncePerDatabase(db, key, fn)` — тот же движок для одного шага (им пользуется `barbar-users.ts`, ключ `identity-bootstrap-v2`).
- `netlify/lib/database/registry.ts` — реестр всех шагов по порядку:
  - `schemaMigrations` — индексы и коллекции, выполняются до импорта или обновления модели учёта (`initialize` в `barbar-mongo.ts`);
  - `dataMigrations` — изменения документов, выполняются после неё;
  - `guestMigrations` — подмножество для публичной функции гостевых заказов.
- Отметки читаются **одним запросом** на объект `Db`, то есть на экземпляр функции. Первый запрос репозитория читает их параллельно с `state`. Пользователи, репозиторий и гостевые заказы в одной функции получают общий `Db` из `mongoConnection`, поэтому на уже мигрированной базе холодный старт делает одно чтение `appMigrations`. Если есть невыполненный шаг, а отметки были прочитаны раньше, перед запуском они перечитываются: шаг мог завершить другой экземпляр.
- Отметка пишется только после успешного шага: `{ _id, completedAt, startedAt, durationMs, description }`, через `$setOnInsert`. Если тот же шаг параллельно выполнит второй экземпляр, в журнале остаётся первое завершение. Отметки прежней версии содержат только `completedAt` и остаются действительными. Упавший шаг отметки не оставляет и выполняется снова при следующем запросе.
- В `dev:production-db` репозиторий и гостевые заказы (`migrations: false`) и пользователи (`bootstrap: false`) миграции не читают и не выполняют. Как и до реестра, исключение одно: локальный `/api/barbar/push` вызывает `ensurePushIndexes`.

Действующие ключи, которые нельзя менять, в порядке выполнения: `ledger-indexes-v5`, `audit-indexes-v2`, `push-indexes-v2`, `2026-09-25-notification-feed-indexes`, `2026-09-25-price-history-indexes` (`schemaMigrations`), затем `food-catalog-v1`, `goods-catalog-v3-<хэш>`, `goods-merge-v3-<хэш>` (`dataMigrations`); отдельно `identity-bootstrap-v2` в `barbar-users.ts`. Хэш каталожных ключей меняется вместе с `barConfig.upgrades`, и тогда шаг выполняется заново. Это предусмотрено: шаг идемпотентен. Тест реестра в `migrations.test.ts` (идёт и в обычном `npm test`, без базы) сверяет все 8 ключей и их порядок со списком `shipped`: переименование или перестановка любого шага роняет тест.

## Как добавить миграцию

1. Опишите шаг рядом с его кодом: `{ id, description, run(db, client) }`. Новый `id` имеет вид `ГГГГ-ММ-ДД-<кратко>`, например `2026-09-25-notification-feed-indexes`.
2. Добавьте шаг **в конец** `schemaMigrations` или `dataMigrations`. Выпущенные шаги не переименовываются, не переставляются и не удаляются. Изменилось определение — новый шаг с новым `id`.
3. Шаг должен быть идемпотентным: несколько холодных стартов могут выполнить его одновременно, а после `db:restore` он выполнится ещё раз, потому что резервная копия не содержит `appMigrations`.
4. Внесите новый `id` в конец `shippedSchema` или `shippedData` в `migrations.test.ts` (из них собирается `shipped`). Так тест защитит ключ от переименования после выпуска. Список `previousRelease` в том же файле не меняется: это отметки версии до реестра.
5. Проверьте на локальной базе: `npm run test:db` и `npm run db:migrate:check` (ниже).

## Правила сохранности данных

- **Только добавление.** Новые индексы и коллекции; новые поля через `$set` только там, где поля ещё нет, или через `$setOnInsert`. Старые данные читаются как раньше: новое поле необязательно в `validateData`.
- **Расширение → переход → сужение (expand/contract).** Переименование или смена формата поля делается в три выпуска: (1) добавить новое поле рядом со старым и заполнить его миграцией, код читает оба; (2) код пишет и читает новое поле; (3) отдельной поздней миграцией удалить старое поле, но только после проверки на копии и свежей резервной копии.
- **Изменения документов — в одной транзакции** (`withTransaction`, `readConcern: snapshot`, проверка `state.revision`), как в `goods-catalog.ts` и `food-catalog.ts`. При изменении каталога нужно обновить `revision` и `catalogRevision`.
- **Запрещено** в миграции: `drop`/`dropCollection`, `deleteMany` и `replaceOne` существующих документов учёта, перезапись пользователей и паролей. Исключение из правил проекта: каталожная миграция может удалить позицию каталога, только если у неё нет закупок, движений, сбросов, продаж, остатка, ссылок в рецептах и архивном использовании.
- **Индексы.** Удалять можно только точные прежние индексы приложения из списка `retired` в `indexes.ts` и только после построения замены. Пользовательские, уникальные, частичные и TTL‑индексы не удаляются.
- Новая коллекция учёта добавляется в `ledgerCollections`, `validateData` (необязательной) и `scripts/db/backup-test.mjs`.

## Проверка на копии базы

```sh
npm run db:start
npm run test:db                                                     # migrations.test.ts и остальные тесты базы
npm run db:migrate:check                                            # синтетический учёт, 20 000 продаж
npm run db:migrate:check -- --without-markers                       # как после db:restore: все шаги заново
npm run db:migrate:check -- --source barbar_copy_<id>               # локальная копия; источник только читается
npm run db:migrate:check -- --source barbar_copy_<id> --without-markers --out docs/perf/<файл>.json
```

`db:migrate:check` работает только с `mongodb://127.0.0.1` или `localhost`. Скрипт копирует источник во временную базу `barbar_migrate_check_<uuid>` вместе с индексами, кроме TTL: истекающие сессии изменили бы копию во время проверки. Затем он делает холодный старт, второй холодный старт и три одновременных, каждый раз через новый объект `Db` и новый репозиторий. После каждого этапа сравниваются число документов и SHA‑256 содержимого в `orders`, `tables`, `sales`, `purchases`, `users`, `sessions`, `stockMovements`, `stockResets`, `expenses`, `shifts`, `suppliers`, `priceChanges`, `alcohol`, `cocktails`, `stockBalances`.

Проверка не проходит (код выхода 1), если:

- изменился хотя бы один документ учёта или пользователей;
- каталог изменился в прогоне, где не выполнялась ни одна миграция данных;
- повторный или одновременный старт изменил данные или журнал отметок;
- после первого старта у какого-то шага нет отметки.

Временные базы удаляются в конце. Копию рабочей базы получают только расшифровкой существующей резервной копии в отдельную локальную базу, см. `docs/database-backups.md`; ради проверки выгрузку из Atlas не делают.
