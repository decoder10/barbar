---
name: barbar-ledger
description: Modify Barbar Cafe inventory, recipes, sales, MongoDB persistence or user permissions while preserving its accounting and role contracts. Applies only to the Barbar Cafe project.
---

Work from the repository root. Read `docs/architecture.md` when locating modules.

- Accounting and saved prices use AMD. Display conversion belongs in presentation code, never in ledger mutations.
- The business day begins at 06:00 Asia/Yerevan. Preserve existing historical dates; use the shared business-day functions for new sales.
- Bottle quantity, bottle size and glass serving size are distinct. A glass sale records its chosen ml and immutable ingredient/cost snapshot. Cancellation reverses that snapshot.
- `domain/model.ts` validates commands; `netlify/lib/barbar-handler.ts` enforces role permissions before repository writes. UI visibility is not authorization.
- Workers receive only `barbar-access.ts` allowlisted data. Selling prices and saved sale revenues are allowed in Sales and its daily summary. Never expose costs, purchase prices, profit, report totals or full ledger objects. They can edit recipes, but cannot change stock, purchases or financial fields.
- Keep command IDs stable on retries. MongoDB transactions and revision checks prevent double sales and lost updates.
- Existing user identities, custom catalog entries and recipes take precedence over bootstrap defaults. Image changes must not reseed data.
- Test ledger changes in an isolated database. `test:db` creates disposable databases; verify their names before adding cleanup code. Do not use production sales as test fixtures. A new Mongo-backed test file must be added to the `test:db` script list in `package.json`; plain `npm test` skips those suites.
- Stock `category` drives accounting (`mixer`/`food` are recipe ingredients, `goods` are sold whole); the product `group` (fruit, snacks, soft drinks…) only organises tabs and ingredient pickers. Keep one physical product as one stock item.
- Goods link to one menu item: each sale deducts `saleAmount` in the item's unit (1 bottle/pc, or grams/ml); `pricePerLiter` of goods is the price of one sale. Bottled goods with `bottleSizeMl` enter recipes in ml as a share of one piece.
- Sets store `components` (tinctures × shots); a set sale expands the tincture recipes and their extra costs. A tincture used in a set keeps its category.
- Catalog upgrades run once per database (`appMigrations`) and must be insert-only or remove only items without purchases, movements, resets, sales, balances or recipe references. Bump the key when the definition changes; never run them for `dev:production-db`.
- Purchase notifications are written in the purchase transaction (`purchaseEvents`, ID = command ID) and delivered to active owners only.
- `GET /api/barbar/catalog/cards` accepts `resources=cocktails,alcohol` (≤2, unique) through `parseCardQueries`; the response is `{ pages, catalogRevision, revision, role }`, stock and the popularity window are read once. Single-resource requests keep the flat shape.
- History pages: `total` and `groups` ride with the first page only; a cursor page is one indexed find and the client keeps the loaded totals (`use-history.ts`). `salesPopularity(from, to)` counts a window of `presets.popularityDays` business days.
- `GET /api/barbar/notifications` (`netlify/lib/notifications/feed.ts`) lists TTL-bound queued events, newest first: owners get purchases and stock, workers stock only. It is a recent feed, not a history.
- Report aggregations run sequentially inside one snapshot transaction on purpose: a MongoDB driver session is not safe for concurrent operations. Do not "parallelise" them inside the session.
- Every public function declares a Netlify `rateLimit` (including `/api/menu` and `/api/barbar/push`); `netlify.toml` sends HSTS. Sale, `createCocktail` and `updateRecipe` pick fields explicitly on the server — keep it that way for any new worker command.
- Server transport lives in `netlify/lib/barbar-handler.ts` (auth, method, origin, route choice) and `netlify/lib/http.ts` (`HttpError`, `respondError`); the work is in `netlify/lib/routes/{cards,catalog,working,commands}.ts`. New routes get their own module and throw `HttpError` for user-facing failures. `salesPopularity` is cached per revision through `queries/cache.ts` — do not add a second cache in front of it.
- Orders: a receipt line is a `Sale` with `orderId`; `Order` holds table, status, actors, payments and `total`, never lines. `payOrder` must receive `expectedTotal` equal to the active lines and methods from `config/payment-methods.json`. Workers get `removeLine` (a line of an open order only); `void`, `saveTable` and `removeTable` stay owner-only. Shared totals live in `domain/orders.ts` (`orderLines`, `orderTotal`, `receiptCount`, `ordersSnapshot`) and `round` in `domain/money.ts`; the domain never checks roles. `execute` loads the touched order, its lines (credited back into balances first) and tables; `readOrders` feeds `GET /api/barbar/orders`. `tables` and `orders` are ledger collections: keep them in backups, `validateData` and `ledgerCollections`.
- Guest table requests (`/api/guest-order`, `netlify/functions/barbar-guest-order.ts` → `guest-order-handler.ts` → `guest-order-store.ts`) are public and unauthenticated. They are GET by table `code` plus optional request `id`, and POST only after `sameOrigin`, with a body of at most 12000 characters and a validated token and code. Rows live in `guestRequests` with a TTL `purgeAt` and return only through `publicGuestRequest` (no tokens, internal order IDs or ledger objects). A guest request never creates a sale; staff turn it into order lines. Keep new guest fields in that projection and respond `no-store`.

## Working copy and writes (`netlify/lib/barbar-mongo.ts` `execute`)

- The server working copy holds stock balances in `opening`, not history. Any sale loaded for a check (void, receipt, batch lookup) goes through `loadSales`, which credits it back so `stock()` still equals the stored balance. Load only the slices a command needs.
- Changed rows are written with `$set`, plus `$unset` of the keys the command removed from a loaded row. Commands clear an optional field with `delete` (not `undefined`), and edit forms send the full row so fields they don't show (favourite, supplier) survive.
- Batch rows (preparations and write-offs aimed at a batch) load only into the in-memory `BarData.batchSources` through `netlify/lib/batch-sources.ts`, for the touched outputs. `compactData` drops them. Never put them in the working copy's `stockMovements`: its balances already include them, so the stock would be counted twice. `batchMovements` in `model.ts` uses `batchSources` when `opening` is set, and the full movement list otherwise.
- A new ledger collection (e.g. `suppliers`, `priceChanges`) must be added to `ledgerCollections` in `database/indexes.ts`, to `validateData` (optional, so old data stays valid) and to `scripts/db/backup-test.mjs`. Index changes are additive and go under a new `ledger-indexes-vN` key; the `retired` list only drops exact legacy indexes.

## Prepared batches (`domain/batches.ts`)

- FEFO: using and writing off stock takes the earliest-expiring batch first, so the balance sits in the latest-expiring batches. Stock the batches don't explain (a purchase, a count surplus) is `unassigned` and is used first, at the residual cost.
- The stored balance and its batch split normally disagree: use before this release and count shortages go at the average cost. So every consumption of a prepared output (a sale via `batchConsumption`, an ingredient of another `prepare`, a batch-targeted `writeoff` in `domain/operations.ts`) caps its cost at the balance cost `max(0, averageCost × stock / priceBasis)`, and taking the whole stock takes all of it. Without the cap the stored cost can go negative and leak into permanently stored sale costs. Test such changes with a deliberately diverged balance, not only with matching batches.
- A sale stores `ingredients[].batches: [{id, ml, cost}]`; void or cancel restores exactly that snapshot. Items without batches and older sales keep the weighted average.
- `correctBatchYield` (owner only) accepts only an untouched batch: its FEFO share is full *and* no active sale references it in `ingredients.batches` (the server finds one with `limit: 1` through the sparse `sale_batches` index). Use by a later `prepare` or a write-off without `batchId` stores no batch snapshot and is not detected. A batch write-off never exceeds the batch's remainder.

## Priority 2 commands and access

- `addLines` (both roles) adds a repeat or bulk set to one receipt. It opens the order with the command id if none exists, line ids are `${id}_${i}`, and at most `barConfig.guest.orders.maxLines` lines are allowed. Prices come from the server; if the computed total differs from `expectedTotal`, the whole set is refused with «Цены изменились». A retry with the same id changes nothing. `GET /api/barbar/orders/recent` resolves "mine" from the session and returns staff lines through `staffSale`.
- Favourites: personal ones are saved with `POST /api/barbar/favorites` (`routes/favorites.ts`, body ≤4 KB, current user only). `setFavorites` in `barbar-users.ts` `$set`s only `favorites`; `domain/favorites.ts` `cleanFavorites` accepts ≤60 unique `kind:productId` keys. The venue favourite is the owner command `setFavorite`; staff receive only the `favorite: true` flag.
- Purchasing (`domain/reports/purchasing.ts`): lead time comes from item → supplier → default, safety days from item → default. Every row carries `leadSource`/`safetySource`, and unset values are shown as such. Suppliers and item parameters are owner-only.
- Price history: `priceChanges` rows are written in the same command, only when an existing item's price actually changes. Nothing changes prices automatically, and there is no history before the release.
- Period comparison (`queries/compare.ts`, `domain/reports/compare.ts`) uses the report's active-sales filter, hours in Asia/Yerevan, and an "unknown" bucket for backdated sales. The mix effect is the remainder, so the parts sum exactly to the revenue delta.
- Owner only: `setFavorite`, `saveSupplier`, `removeSupplier`, `correctBatchYield`, `/api/barbar/report/compare`, `/api/barbar/prices` and `/api/barbar/batches` (401 when logged out, 403 for a worker, before any database read). Staff data and responses never contain `suppliers`, `priceChanges`, `batchSources`, supplier or lead/safety fields, sale `batches` or `plannedQuantity`. Add any new private key to `noPrivateFinancialData` in `netlify/lib/barbar-access.test.ts`.
