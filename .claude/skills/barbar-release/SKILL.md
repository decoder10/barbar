---
name: barbar-release
description: Verify and release authorized Barbar Cafe changes to its Git repository and Netlify, with concrete checks and preservation of live data.
---

- Inspect the working tree and current branch; honor the user's authorized destination. Skill use alone does not authorize a push or deployment.
- Run `npm run check`, `npm run build` and relevant Playwright scenarios. For persistence changes, run `test:db` against a separate local MongoDB test database: plain `npm test` skips every Mongo-backed suite, so its pass does not cover them. Use `scripts/benchmark.mjs` for comparable synthetic inventory measurements.
- Never commit `.env`, credentials, local ledger files or test artifacts. Bootstrap secrets are server environment variables.
- Verify catalog/photo edits preserve existing IDs and recipes. Do not reset production or local business data to make a test pass.
- Netlify uses `netlify.toml` and Functions. Confirm the deployed commit or changed build assets after an authorized push; an HTTP 200 response alone does not prove the new release is live.
- Check the deployed login page and anonymous API behavior without creating production test sales. Report cloud settings that cannot be verified, including backup and network configuration, as unverified.
- Anonymous probes for the owner/staff routes added in Priority 2 must return 401: `/api/barbar/favorites`, `/api/barbar/orders/recent`, `/api/barbar/report/compare`, `/api/barbar/prices`, `/api/barbar/batches`; `/api/barbar/auth` returns `authenticated: false`.
- Update release notes with actual checks, material limitations and any user action needed. Do not describe incomplete work as finished. A check that could not run (no Docker/MongoDB, busy port, no network, no password) is recorded as "not run" with the reason, never as passed, and does not block the rest of the work.
- Before a release also run `npm run test:backup` and `npm run test:scheduled-backup`. Report storage with `npm run db:storage` when Atlas access is available, and latency with `npm run probe:latency` after publishing (anonymous GETs only).
- One-time catalog migrations run on the first API request after deploy; mention them in release notes. `dev:production-db` (port 4002) is never used for tests.
- `dev:production-db` binds `--host localhost --port 4002` and opens `http://localhost:4002/` (Vite `open`, disabled when `CI` is set); `127.0.0.1:4002` is intentionally not served. In production mode `server/local-api.ts` runs no migrations and bootstraps no users — keep it that way.
- Migrations are `appMigrations` markers listed in `netlify/lib/database/registry.ts` (schema/index steps and data steps; see the `barbar-migrations` skill and `docs/database-migrations.md`; keep `docs/production-release-rules.md` R04 in sync). They run on the first real API request after deploy, including the public `/api/guest-order` with a valid table code (`guest-order-store.ts` `ensureReady`). `db:storage` does not report migration keys: confirm them with read-only `appMigrations` and `listIndexes` reads, or mark them unverified. Never write to Atlas just to trigger a migration. A local database that already ran a marker does not pick up later additions under the same key. Before a release `npm run db:migrate:check` (local MongoDB) restores a copy and reports steps run, marker reads and data changes.
- Anonymous production probe for guest requests: `GET /api/guest-order` without a code or with a malformed one returns 404 before touching the database; never POST a cart to production.
- `npm run test:load` reports history first-page and deep-page timings plus the explain counts; compare `historyDeepPage` against `historyFirstPage` after query changes; it also reports `cardsPopularCold`/`cardsPopularCached` and the popularity explain. After `npm run build` check the chunk table: `react`, `main`, `photo-manifest`, `photo-catalog` and the per-route chunks; both `index.html` and `guest-menu.html` must preload the same shared files. Compare the URLs of shared `react`, `photo-manifest` and `photo-catalog` chunks, not equality of the entire preload lists: the guest entry can additionally preload its own UI/icon chunks. `npm run perf:bundle` reports first-screen size and whether the seed catalog is in it. `dist/barbar` should contain `bar-hero.jpg` as the only JPG.
- Playwright does not start the dev server. `playwright.config.ts` takes `baseURL` from `BARBAR_E2E_BASE_URL` (default `http://127.0.0.1:4001`), and specs use the `baseURL` fixture, so no spec hardcodes a port. To avoid the owner's 4001 server and its database, start a separate one: `BARBAR_MONGODB_DATABASE=<temp name> npx vite --host 127.0.0.1 --port 4011 --strictPort`, run `BARBAR_E2E_BASE_URL=http://127.0.0.1:4011 npx playwright test ...`, then stop it and drop the temporary database (see README). Never stop or reuse a server the owner started. `GET /api/barbar/environment` in `server/local-api.ts` returns `{ database: 'local' | 'production', name }` without accessing the database; it identifies the profile, not connectivity or isolation.
- After an e2e or migration run against a local database, compare read-only counts (`appMigrations`, orders, sales) before and after to prove the owner's `barbar` database was untouched.
- A function `config.path` must never equal a static page `<path>.html` in `dist`: Netlify answers 500 before the function runs (see barbar-netlify-functions skill).
